# Glicko-2 按场结算与历史重算：评审草案

日期：2026-11-12。

本文整理本轮讨论提出的候选方案，供其他人独立分析。**尚未批准实施，未修改业务代码。** 不将另外两份结算文档中的算法、参数或约束视为已经确定。

## 1. 目标与当前结论

产品负责人的目标是：积分尽量反映球友的真实实力。目前没有确定必须沿用 Elo，也没有确定补结算只能计算本场。

将目标具体化：用比赛前的实力估计，较好预测之后的胜负；新人能较快定位，稳定用户不过度受单次爆冷影响，实力变化能得到反映。

本轮推荐的候选方向：

1. 用 Glicko-2 保存实力分、估计的不确定程度和波动程度。
2. **一场首页发起的比赛作为一个批次，整场统一结算，不按天合并。**
3. 场内使用统一赛前快照，综合每个人在本场的全部已记录胜负更新一次实力。
4. 各场按实际比赛时间形成固定顺序。
5. 补结算早期比赛后，重新计算受影响的后续历史，允许历史积分变化。

这不是已经验证的“最佳算法”。Glicko-2 是否优于调好的 Elo、计分周期是否适合本产品，均需要验证。历史重算解决的是时间顺序一致性，本身不保证实力估计准确。

**主要代价必须明确：影响可能通过后续对手传播。即使 E3 和补结算的 E1 没有共同参赛者，E3 也可能需要重算，不能保证范围很小。**

## 2. 与当前代码的对应关系

本方案针对首页“开比赛”、每组 8～12 人的比赛，不针对已经删除的“我的”中的单独约战功能。

目前检查到的结构：

- `events`：整场比赛，含 `startTime`、状态、胜负结果。
- `signups`：报名和组号；`eventSchedule.startEvent` 按人数分组。
- `matches`：一条两人对阵的记录，通过 `eventId` 关联整场比赛。
- `eventSchedule` 的 `report` / `set` 保存胜负，并 upsert 对阵；当前写入的 `scoreChange` 为 0，不修改用户积分和场次。
- `eventSchedule` 尚无整场积分结算入口。
- `users` 当前只有 `score` 等统计，没有 Glicko-2 的完整状态。
- `updateEvent` 目前允许直接将状态设成 `finished`；正式实施结算时需要关闭这条旁路。
- `getUserProfile` 当前按对阵记录生成折线，筛选非零变化，并以记录创建时间排序；需要随按场方案调整。

“一场”与“对阵”必须分开称呼：一场比赛可有多个组，每组有多条两人对阵。结算单位为整个 `eventId`，不是单条 `matches`，也不是一天。

## 3. Glicko-2 保存什么

每个用户保存完整状态，而不只保存总分：

```text
rating：实力分
RD：对实力估计的不确定程度，越大表示越没有把握
sigma：模型中的波动参数
lastRatingTime：上次处理实力状态的时间
```

含义：同为 1500 分，只有 2 条成绩的人与已有 100 条成绩的人，系统对他们的把握不同。新成绩带来的调整不必相同。

久未比赛应增加估计的不确定程度，而不是直接认定实力降低。具体如何把自然时间映射到模型周期，见第 10 节，尚未确定。

初始化、RD 上下界、sigma 初值、tau 等参数尚未确定。原项目用户初始分为 1000；官方算例常用 1500。展示起点不能直接照抄，需统一初始状态和标尺。

Glicko-2 不要求每场所有人的增减总和为零，不应额外强行配平胜者加分与败者扣分。

## 4. 一场比赛如何计算

例如一场 8 人比赛，A 有 7 条已记录胜负。输入是 A 本场前的完整状态、7 个对手本场前的完整状态、这 7 条胜负；输出是 A 本场后的完整状态。

所有人的输入来自同一份赛前快照。不能先更新 A，再拿 A 更新后的状态计算同场 B。

```text
计算一场(event, 历史状态表)：
    对阵 = event 中已经记录且纳入结算的有效胜负
    参与者 = 这些对阵涉及的用户

    赛前快照 = 从历史状态表复制参与者的完整状态
    按统一的时间规则处理每个人的赛前不确定程度

    对每个参与者 u：
        成绩列表 = []

        对 u 参与的每条对阵：
            加入：对手的赛前状态 + u 的胜负

        赛后状态[u] = 标准Glicko2批次更新(
            本人赛前状态 = 赛前快照[u],
            成绩 = 成绩列表,
            算法参数 = 固定版本参数
        )

        本场积分变化[u] = 赛后状态[u].rating - 赛前快照[u].rating

    全部算完后：
        将赛后状态一起放入历史状态表
        返回每个人的赛前状态、赛后状态和本场变化
```

注意：

- 只有已记录的实际交手参与计算；没打完不补成负，没交手不虚构结果。
- 一个组的结果不直接作为另一个组的成绩。
- 没有任何有效对阵的人不生成一次比赛更新。
- 记胜负的先后顺序不影响本场结果；实现还应固定遍历顺序，避免浮点累加顺序造成差异。
- 建议内部保留足够精度，展示时才取整；不能用展示整数相同来认定完整状态相同。

这里的 `标准Glicko2批次更新` 必须使用经过官方算例验证的实现，不是自行拼接的“赢了加更多”规则。其正式步骤包括尺度转换、期望成绩、方差、表现偏差、波动参数求解及 RD / rating 更新，参考文末原始说明。

## 5. 各场如何排序

候选规则：

```text
排序键 = (events.startTime 对应的实际比赛时间, eventId)
```

- 时间按明确时区解析，项目使用北京时间。
- 同一天上午和下午的比赛分开结算。
- 排序不使用录入胜负时间，也不使用点击结束的时间。
- 完全相同的开始时间用固定 ID 顺序打破平局。这仅保证确定性，不代表真实先后已被准确还原。
- 若同一人参加重叠比赛，按整场作为一个批次只能近似描述先后关系，需要明确产品规则。
- 已结算后修改开赛时间会改变历史顺序，应禁止随意修改，或通过同样的历史纠正流程处理。

这里的“赛前状态”是按已纳入结算的历史重建出的本场之前状态，不是报名时冻分，也不是管理员补点结束时直接读取的当前分。

## 6. 为什么 E3 可能被 E1 影响

```text
E1（周一）：A、B、C……参加，忘记结束
E2（周三）：A、D、E……参加，已经结算
E3（周五）：D、F、G……参加，已经结算
```

补结算 E1 后：

1. A、B、C 等人的历史状态得到更新。
2. A 进入 E2 的状态改变。若 D 在 E2 和 A 交过手，D 的计算依据改变，D 的赛后状态可能改变。
3. D 进入 E3 的状态随之改变，D 及其在 E3 的对手可能需要重新计算。

**E1 与 E3 没有共同参赛者，仍可能通过 E2 的 D 连起来。** 胜负记录保持不变，重新计算的是实力状态及积分变化。

场内传播有边界：E2 所有人都使用 E2 赛前快照。因此 D 的赛后状态变化不会在 E2 内继续传给另一个只与 D 交手、未与 A 交手的人；D 的新状态会用于他后续参加的比赛。

若某场与这条向未来传播的对阵关系没有连接，其结果不受影响。基础实现可以仍计算它，再跳过不变的写入；精确筛选范围属于后续优化。

## 7. 补结算的基础实现：从历史检查点重放

首先采用容易核对正确性的版本，不预先承诺传播很快消失。

```text
结束比赛(target)：
    校验操作权限、比赛状态和已记录胜负
    防止重复结算，并建立一致的计算输入版本

    起点 = target 排序位置之前的最近一个有效历史检查点
    历史状态表 = 恢复检查点中的完整用户状态

    队列 = 检查点之后已纳入结算的比赛 + target
    按固定排序键排序，去重
    // target 之前、但位于检查点之后的比赛也必须重放

    对队列的每一场 event：
        新结果[event] = 计算一场(event, 历史状态表)

    对比新旧结果
    用一致的发布机制保存本轮结果
    更新用户当前完整状态、历史记录、target 的结算状态
```

检查点需要包含相关用户完整状态、时间信息、算法版本与参数版本。不能仅用“当前分减后续 scoreChange”恢复 Glicko-2，因为 RD、sigma 也需要恢复。

如果没有可用检查点，原则上从可信的初始状态重放。已有用户、旧对阵或人工改分如何形成可信初始状态，需要迁移设计，不能直接清零覆盖。

未结束的其他比赛仍不纳入计算；后面的比赛可以照常结算。以后再补入更早的比赛时，再进行历史纠正。

当最终纳入的比赛、胜负、初始状态、参数版本和固定排序相同时，确定性的完整重放应得到相同结果，不受点击结束的顺序影响。这不表示中途缺少成绩时的临时积分也相同。

## 8. 性能优化的边界

可以区分三种成本：读取多少历史、内存计算多少场、最终写入多少条记录。减少数据库写入，不等于减少全部重算成本。

后续可以优化：

- 用历史检查点避免从注册开始计算。
- 只沿受影响选手的后续真实对阵传播。
- 只写完整结果确实变化的记录。
- 通过任务队列处理较长的重算，完成后统一发布版本。

优化必须保持与基础完整重放等价，尤其注意：

- rating 相同但 RD / sigma 不同，后续结果仍可能不同。
- 展示分取整相同，不代表内部状态相同。
- 不能保证三层传播后变化归零。
- 即使每次变化很小，也可能跨过取整边界；不能拿“少于 0.5”直接证明整数结果不变。
- 按精度阈值截断传播会成为近似算法，必须说明误差和顺序一致性的影响，不能继续宣称与完整重放完全一致。
- 不能随意规定超过 14 天只补本场积分，又同时宣称所有历史均按时间严格一致。是否设置期限是额外产品取舍，本草案没有采用。

最坏情况下影响可能覆盖大量后续比赛。尚未用本项目数据测量，不能宣称服务器成本很低，也没有毫秒级耗时承诺。

## 9. 展示方式与当前结构的差异

推荐实力折线一场比赛一个点：

```text
本场：4 胜 3 负
实力分：1000 → 1035（+35）

下方逐条展示对手及胜负。
```

以上分数仅为展示示例，不是公式计算结果。

- 点的时间取比赛实际时间，纵轴取该场计算出的赛后实力分。
- 补结算后，受影响的历史点随新结果一起更新。
- 本场有有效对阵且已结算，即使积分变化为 0，也可以保留一个点。
- 不把 RD 在无比赛期间的变化误画成实力分下降。

**Glicko-2 的自然输出是每个人本批次的状态变化，不天然提供每条对阵一个独立的整数加减分。** 因此不能直接沿用“每局 scoreChange 加总就是本场变化”的旧设计。

建议增加每场每人的结算记录，保存赛前、赛后状态及本场变化。若仍坚持逐条对阵展示加减分，需要另行定义可解释的分摊规则，不能把任意分摊说成算法原生结果。

整数展示也要统一规则。例如可显示“赛后展示分 − 赛前展示分”，避免单独四舍五入变化值后与两端分数对不上。内部状态继续保留精度。

## 10. 必须在开工前解决的模型问题

### 10.1 按场批次与自然时间如何配合

Glicko-2 的正式说明以 rating period 为单位；作者指出每个周期平均有一定比赛量时效果较好，示例建议平均每人至少约 10～15 场两人比赛。项目每组 8～12 人，完整循环赛每人 7～11 条对阵，实际可能更少。

所以“每场 event 一个批次”是需要验证的应用选择，不应直接认定为最优计分周期。

尤其不能把平台上每一场无关比赛都当作全体用户又经历一个空闲周期，否则其他地区活动越多，一个不打球用户的不确定程度就涨得越快。

需要明确：

- 一场批次中的 sigma 如何解释、校准。
- 两场相隔几小时或几个月，不确定程度怎样随自然时间变化。
- 如何避免既按自然时间增长不确定程度，又在标准公式里重复计入同一段空闲。
- 若使用时间缩放的 Glicko-2 变体，必须给出正式定义，与未经修改的标准算法区分。

**本草案还没有确定这部分公式，是开工前的阻塞项。**

### 10.2 参数与准确性验证

不能仅凭算法名称承诺“最真实”。建议与当前 Elo、调参后的 Elo、必要时原版 Glicko 对比：

1. 严格按时间切分数据，仅用较早已知成绩预测较晚比赛，避免信息泄漏。
2. 比较胜负预测的对数损失、Brier 分数和胜率校准。
3. 单独观察新人定位速度、稳定用户波动、久未比赛用户和高手群体。
4. 用真实补结算场景验证顺序一致性及运行成本。
5. 区分“事后补齐历史的积分”与“当时系统实际已知的信息”，不能拿事后重建分直接冒充当时可做出的预测。

数据量不足时，结果只能支持有限结论，不能宣称某个参数已经最优。

### 10.3 数据局限

长期只在各自圈子内打球、缺少跨圈对阵时，不同圈子的绝对实力难以比较。虚拟球友必须保持稳定身份，否则同一个人反复被创建成新人，会削弱模型判断。

算法也不能仅凭录入的胜负识别让球、随意打或错误成绩；可靠的比赛数据仍是前提。

## 11. 工程一致性要求

这里只列影响正确性的必要要求，不代表已经定好实现：

- 同一场结束两次不能重复计入；结算中不能继续改胜负。
- 多场同时结束可能影响相同用户或历史区间，仅有每个 event 自己的锁不够。需要统一任务串行、版本校验或其他等价的并发协议。
- 重算失败不能让用户表已更新而历史表只更新一半。需要事务或分批写入加版本发布机制，并支持恢复和幂等重试。
- RD / sigma、当前分、历史结果、检查点必须属于可对应的算法版本。
- 补重算不应重复增加胜负场次；新增计入比赛与纠正既有积分应分别处理。
- 用户注销后保留历史身份和必要状态；当前软删除设计有利于此。
- 旧单局记录是否作为历史输入，需要根据实际数据库审计后确定，不恢复已删除的单独约战功能。
- 暂不引入信用、自动结束、报名费或其他无关功能。

## 12. 希望评审者给出的结论

1. 对本项目的单打分组比赛，Glicko-2 比调好的 Elo / Glicko 是否有足够收益？不能只比较算法复杂度。
2. 每场 event 一个批次是否合适？自然时间与空闲不确定程度应如何正式定义？
3. 为得到时间一致的实力估计，允许影响传播到没有参加原比赛的人，是否值得？若不值得，应明确提出接受什么近似和误差。
4. 历史检查点、最小传播范围、并发结算和原子发布，怎样实现才足够简单可靠？
5. 是否认可改成“本场总变化 + 对阵胜负明细”，放弃每条对阵一个独立加减分？
6. 用什么实际数据、基线与指标决定最终选型？

请重点分析缺点和未解决的问题，而不是把本草案直接当成开工方案。
