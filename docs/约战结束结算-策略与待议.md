# 约战结束结算：当前策略与待议问题

供其他 agent 审阅。本文只讨论设计，代码尚未开工。产品是微信小程序「乒乓球约战」（仓库 `my-pingpang`），竞品是「小 i 约球」，不要写成竞品名。

作者口径截止：2026-11-12。下方「已倾向」是和产品负责人（赛梁）讨论后的现行折中，尚未说「按这个做 / 开工」。请重点挑逻辑漏洞、和「积分反映实力」目标是否打架，以及有没有仍只算一场、但更自洽的算法。

---

## 1. 背景与硬约束

- 约战进行中只记胜负，不预计算加减分，不改 `users.score`。积分在「结束比赛」时一次性结算。
- 单独记一局、当场改积分的入口已删除（原先 `createMatch`，`matchType: friendly`）。库里可能还有旧记录。约战结算拟复用同一套 Elo，不换 Glicko / TrueSkill。
- 原先 Elo：期望分 `1 / (1 + 10^((对手分 - 自己分) / 400))`；K：积分 `< 1500` 用 32，否则 16。约战按胜 1、负 0；平局不改 Elo。一场约战里多局对阵，用同一份结算基准快照平行计算再加总入账，不按场内记分顺序滚分。代码里这套结算还没做。
- 基准分用「结算时的分」，不是报名或开赛时冻住的分。
- 发起人知道别人还有更早的场没结束，也做不了什么。因此不采用「有更早未结算场就不让结束」。
- 一场一直不结束，不能卡住这个人后边几天的比赛（那些场仍可正常结束、入账）。
- 管理者忘了点结束，系统无法从根上避免。设计要能补结算，但不能假装能完全防止这件事。
- 用户希望积分体系较好反映实力，也希望补结算时尽量只算被结束的那一场，不要把后边已入账的比赛整段重放。
- 折线图必须按实际比赛日，不按结算时间。每个点表示「那场打完后的分数」。补算一场之后，该日之后已画出的点也要跟着改（见第 3 节），不是只改当前分、留下一段跳变。
- 这轮不做：到场 / 信用、球馆挂接、后台、淘汰赛自动排表、报名费、换 MySQL、公开云存储、信用连胜 / 主持加分、自动结束（全组打完就结束）。
- 现有报名 / 开启 / 记胜负交互尽量不动。结算后不能再改判、再记分；名单和对战表仍可翻。未记下的局不算分，结束确认时要说明。二次结束不重复加分。编辑页现在可以直接把状态改成已结束且不算分，这条旁路要关掉，改走详情页「结束比赛」。
- 虚拟球友按普通人一样入账。个人主页在结算后补上该场加减分（对手、胜负、加减、日期），暂不做「本场合计 +N」行。

## 2. 现行策略：只结算这一场，倒推基准分

只处理发起人正在结束的那一场。不重放该日之后已经入账的约战或友谊赛，也不改那些场当时写下的 `scoreChange`。

### 2.1 倒推基准

对这场里每个要计分的人：

```
基准分 = 当前 users.score − 该人在「本场比赛日之后」已入账的全部 scoreChange
```

含义：把后边已经加进去的分先剥掉，得到「假如当时已经结算到这一天」时，这个人大概会是多少分。场内所有对局都用各自的这份基准快照平行算 Elo，加总得到本场净加减。

然后：

- 把本场各局的 `scoreChange` 写到对应 `matches`（约战对阵在进行中已存在，当时 `scoreChange` 为 0）。
- 把本场净加减加到这几个人当前的 `users.score`。
- 不改写后边那些场的 `scoreChange`。

比赛日之后仍未结算的场，其加减分还不存在，倒推时先不加也减。等那些场各自被结束时，再用同一套方法算。

正常按时结束时，倒推项为空，基准就是当时的当前分，与「按已入账历史接着往下算」一致。

### 2.2 例子

假设某人现在 1080 分，其中 4、5、6 号已入账的净加减合计 +80。1 号当时没结束，现在补结算，按倒推基准 1000 来算，本场净 +40。

- 当前积分改为 `1080 + 40 = 1120`。
- 4、5、6 号每场当时显示的加减分不变，不会在那几场上再各记一次 +40。
- 1 号这几局的 `scoreChange` 按 1000 基准算出并入账。

若 2、3 号也还没结算：补算 1 号时倒推仍只减 4、5、6 的已入账分，不把 2、3 算进去。

## 3. 折线图怎么画

横轴按实际比赛日（不是结算日）。纵轴是打完该场后的累计积分。

实现上不需要改写 4、5、6 的 `scoreChange`。只要 1 号按正确的比赛日写入本场 `scoreChange`，折线按比赛日依次累加所有已入账变化，后边的点会自动抬高。

接上面的例子（数字仅示意 4–6 的拆分）：

| 点 | 补算前（图上） | 补算后（图上） |
| --- | --- | --- |
| 1 号 | 无此点（尚未入账） | 1040（倒推基准 1000 + 本场 +40） |
| 4 号 | 当时入账后的分，例如 1020 | 1060（原累计 +40） |
| 5 号 | 例如 1050 | 1090 |
| 6 号 | 1080 | 1120 |
| 当前分 | 1080 | 1120 |

也就是：每个点都是「按比赛日排下来，打完那场时的分数」。不会出现 6 号还停在旧的 1080、最后一段再跳到 1120。

## 4. 已经否掉的做法

1. **开赛冻分、进行中就预计算加减分**：已明确进行中只记胜负，结束再算；基准不是开赛冻住的分。
2. **有人还在更早开始、仍进行且未结算的比赛里，就不让结束，并提示是哪一场**：发起人知道了也无济于事。
3. **补结算时直接用「现在的当前分」当很久以前那场的基准**：后边几天可能已经把分拉得很高或很低，用 6 号之后的分去算 1 号不合理。
4. **1、2、3 都未结算、4、5、6 已结算时，三场各自用自己被结束那一刻的当前分、互相平行、互不影响**：若 1 号全胜，按理应改变 2、3 的基准，平行快照做不到这一点。
5. **从该场比赛日起，重放后边所有已入账的约战和友谊赛**（不限被波及的人）：积分路径更自洽，也更接近常见技能分做法，但会改写已显示的加减分，计算量随历史对局增长。负责人明确希望仍只算一场。先前一度倾向过重放，后改口。

曾讨论「只重放被波及的人的后续比赛」。对手的分一变，期望分也会变，传染面仍可能扩得很开，当时没有采用，也没有细设计。

对照过的外部实践（仅作讨论，未决定照搬）：FIDE Elo、USATT 赛前快照并按比赛日处理锦标赛、Codeforces 按场次时间顺序、Glicko / TrueSkill 的 RD / 久疏波动。ATP 这类滚动窗口积分不适合「赢更强的人加更多」这一目标。FIDE 对晚提交成绩，常见是用交成绩时的名单分、不改已公布月榜；若更追求技能准确，则是按比赛日重放。这轮不换公式。

## 5. 请重点看的疑问

### 5.1 图上的累计分，和当时用来算 Elo 的分，会分叉

这是现行折中最大的裂缝。

4、5、6 号当时是按「还没有 1 号结果」的分算出 `scoreChange` 的，这些加减分不再改。但折线把 1 号的 +40 插回比赛日之后，4、5、6 的累计点都会抬高。于是：

- 图上「打完 4 号时的分数」已经包含 1 号的 +40；
- 4 号那场 Elo 用的基准，其实没有这 +40。

图和账都「看起来」连续了，对局强度评估仍停在旧历史上。这样还算不算「那场打完的分数」？对「积分反映实力」的伤害有多大？偶发忘结束能不能接受？

### 5.2 多场补结算的顺序，会导致结果不同

这是比 5.1 更实质的正确性问题。

1、2、3 未结算，4、5、6 已结算。若先补 1 再补 2、3：2、3 的倒推里已经含 1 号净加减，相对合理。若先补 3 再补 1：3 会按不含 1 的基准入账；1 随后入账只抬当前分和折线累计，不会重算 3 的 Elo。先补 2 再补 1、或打乱顺序，都会得到不同积分。

「等各自补结算时再用同一方法」并没有消除顺序依赖。有没有在「仍然只改被结束这一场的 `scoreChange`、不重放后边场」的前提下，让补算顺序不影响最终积分的办法？如果没有，是接受顺序依赖，还是必须回到某种重放 / 排队规则（例如按比赛日强制顺序补算，或补算时只允许结束当前最早的未结算场——这又接近已否掉的硬拦）？

### 5.3 倒推是否计入友谊赛，同一天的边界怎么切

现行表述是减「本场比赛日之后已入账的全部 `scoreChange`」，按字面应包含之后的友谊赛，否则约战和友谊赛会割裂。这一点需要确认。

同一天既有约战又有友谊赛，或同一天多场约战：倒推的「之后」按比赛日（当天都算同一天，还是当天内按开始时间 / 结束时间 / 录入时间再排序）？切错一天，基准会偏。晚结束的场，比赛日仍应落在实际打球那天，不应落到补点结束的那天——这一点产品已定，实现时要保证日期字段用比赛日。

### 5.4 「只算一场」和「反映实力」能不能同时成立

负责人既希望积分很好反映实力（接近按时间顺序的技能分），又希望补结算只动这一场。倒推基准是为了给「当时」一个更合理的起点，但后边已入账对局的期望分不再纠正，积分史会留缺口（见 5.1、5.2）。

请评估：

- 这个折中在「偶发忘结束、偶尔补算」下偏差是否可接受；
- 若忘结束变多，或未结算场跨度很长，会怎样恶化；
- 有没有负担可接受、又比倒推更自洽的第三方案，例如：只重放被波及的人、按比赛日重放但对已显示加减分做明确提示、或对超过某时间跨度的补算改用另一种规则。

先前否定全量重放，部分是担心「后边所有比赛都重算」的服务器负担，不单是改已显示分数。若重放范围缩小到「与这些选手后续对局有关的最小闭包」，负担和正确性如何权衡，也希望一并看。云开发事务写数有限，若做重放或大批量回写，需要结算中锁和幂等（例如 `events.settled` / `settledAt`），方案里还没定稿。

### 5.5 折线「点上的分」具体怎么定义，避免再歧义

已对齐的意图：点 = 按比赛日累加已入账 `scoreChange` 之后的分数；补插入更早的场后，后面的点跟着抬；不改后面场的单场加减。

还需要写死的细节：

- 同一天多场，点是每场一个，还是一天一个（用当天最后一场之后的分）？
- 当前个人主页是「近 40 场有积分变化的局」。约战补结算后，这些局会从「无加减」变成「有加减」，应插入折线。点数不够时如何截取，要不要保证补进来的更早场能看见？
- 若只画「有积分变化的局」，一场净 0 的结算还出现在折线上吗？（建议：结算过的场即使净 0 也占一个点，避免和未结算混淆；这点未拍板。）

### 5.6 其他实现向、但会影响规则的点

- `users.score` 必须以「加上本场净加减」更新，并与按比赛日累加全部已入账 `scoreChange`（加初始分）一致，否则图上最后一点会对不上当前分。有没有历史脏数据 / 人工改分 / `fixVirtualScores` 这类补丁会造成漂移？
- 结算中途失败、并发两点结束、同一人同一天多场同时补算，如何锁和幂等，避免加两次分。
- 名单中途退赛、未打完的人：只给已记录对局算分，已定；这些人的倒推基准是否仍用同一公式（是），是否要在确认文案里写清。
- 虚拟球友同样倒推、同样入账，管理侧硬删若发生在结算前 / 后怎么处理，本文不展开，但审阅时若有积分风险请指出。
