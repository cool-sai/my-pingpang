# 涟漪积分法（Ripple-Elo）：乒乓球约战积分与结算方案

> **方案定位**：面向「乒乓球约战」小程序（8～12 人小组循环赛）的积分计算与结算设计。
> **核心目标**：积分稳定地反映球友水平；晚点结束（补结算）也不产生历史烂账和折线图分叉；数据库只写真正变了的记录。
> **状态**：已实现。云函数 `finishEvent`，纯算法 `cloudfunctions/finishEvent/rating.ts`，单测 `npm run test:rating`。
> **本版修订**：相对初稿修正了——示例数字、取整偏差、锁与写入的原子性、记分与结算的竞态、超期兜底的自相矛盾、`users.score` 的覆盖方式、「涟漪几乎必消失」的夸大说法。

---

## 为什么叫「涟漪积分法」？

晚点结束的比赛插回历史时间轴，对后续积分的影响像石子入水：

1. **中心**：本场参赛者积分正常算出；
2. **第一圈**：当事人后续直接参加的比赛，因为进场基准分变了，他参与的那几局加减分会微调；
3. **往外几圈**：对手身上的微调在 Elo 公式里被大幅衰减，再经取整，**多数**变成 0，少数仍会 ±1，继续往后传。

程序不在代码里硬编码「传几层」，而是把重算窗口内的比赛在内存里**完整按时间顺序重放**，最后只把**取整后整数真正变了**的局写回数据库。结果顺序无关、折线图零分叉。

> [!NOTE]
> 涟漪消失是**概率性**的，不是确定的。单局受 `Δ` 分扰动，取整后改变的概率约等于 `K × 0.0014 × Δ`：扰动 7 分时单局约 24%，1 分时约 3.5%。一个人一场打 7～11 局，所以第三圈仍有可观概率出现 ±1。
> 另外，**固定的球友圈子（总是这批人互相打）里，涟漪会覆盖窗口内几乎所有局**（单测里 8 人固定圈补最早一场，后面每场 28 局全部被改写）。这是正确的，不是 bug；写入量被 14 天窗口封顶。

## 一、单场怎么算分

所有人（含虚拟球友）初始 **1000 分**。进行中只记胜负，不改积分；发起人点「结束比赛」时按下面规则一次算完。

### 1.1 场内平行快照
同一场内无论分几组、每组几局，所有人每一局都用**进入本场时的同一份基准分与局数**计算，不在场内滚分。

### 1.2 期望胜率（标准 Elo）
$$E_A = \frac{1}{1 + 10^{(R_B - R_A) / 400}}$$

### 1.3 三档动态系数 K
| 阶段 | 判定条件（按本场之前的累计已结算局数 `totalMatches` 和基准分） | K | 同分单局输赢 |
| :--- | :--- | :---: | :---: |
| 新手定级期 | 累计 `< 10` 局 | 40 | ±20 |
| 成长期 | `≥ 10` 局且 `< 1300` 分 | 24 | ±12 |
| 稳定期 | `≥ 10` 局且 `≥ 1300` 分 | 16 | ±8 |

> 注意：新手期按**局数**计。8～12 人一组每人一场固定打 7～11 局，所以第一场之后若累计仍不足 10 局（组只有 8 人），第二场仍是 K=40。这是有意保留的行为。

### 1.4 新手保护盾
老球友（已打 `≥ 10` 局）输给定级期新号（`< 10` 局）时，老球友本局扣分系数减半（`K_eff = 0.5K`）。新号赢球仍按 K=40 全额加分。

### 1.5 循环赛多局阻尼
1. 每局原始变化：`Δ_i = K_eff × (S_i − E_i)`（赢 `S=1`，输 `S=0`）。
2. 阻尼系数：本场该选手有效局数 `N ≤ 4` 时 `D = 1`，否则 `D = sqrt(4 / N)`。
3. **注意**：小组赛每人 7～11 局，所以阻尼实际上**总是生效**（`D` 约 0.60～0.76），相当于按组人数缩放 K，12 人组的人单局分比 8 人组少。这是有意设计，不是「超过 4 局才偶尔打折」。

### 1.6 取整：按人按场净值取整，再分摊到每局
- 初稿是每局单独四舍五入。问题：强者赢弱者的期望增量常常小于 0.5，被取成 0，输球却扣满，等于强者对弱者期望值为负。
- 现在：一个人本场各局 `Δ_i × D` 先**求和再取整**得到本场净变化 `net = round(Σ Δ_i × D)`，再用**最大余数法**把整数分摊回每一局，保证 `Σ scoreChange_i = net`，且每局与小数值相差不超过 1。
- 分摊是确定性的（按局序、残差、下标排序），重放结果可复现。

## 二、点击「结束比赛」怎么结算

### 2.1 比赛时间锚点 `matchTime`
一律以比赛实际开赛时间为准（`events.startTime`，`YYYY-MM-DD HH:mm`，按**东八区**解析，不能用云函数 UTC 默认解析），不用点击结束或记分的时间。同一分钟的两场按 `eventId` 字典序稳定排列。

### 2.2 天然检查点
每次结算给每局 `matches` 写 `preScore`（双方进入本场时积分）、`preMatches`（双方进入本场前累计局数）、`settled`、`matchTime`。从某时间点 $T_0$ 往后重算时，一个人**在队列里最早那场已结算比赛的 `preScore/preMatches`** 就是他在 $T_0$ 的精确起点；队列里没有他的已结算比赛，则取当前 `users.score / totalMatches`。

### 2.3 结算流程（`finishEvent`：关盘入队 + 工人排空）
1. **鉴权与关盘入队（不抢全局锁）**：仅发起人或超级管理员；未开始拒绝；`events.settled` 已为 true 直接返回。在事务里把 `status` 置为 `finished`（锁死记分）。只要置成 `finished` 且未 `settled`，这场比赛就进入了「待结算队列」，**多人同时点结束互不阻塞**。
2. **抢全局结算锁做消费**：`counters/settlement_lock`，带随机 `token` 的原子条件更新（`locked=false` 或 `lockedAt` 超过 90 秒）。释放时校验 `token`，不会误放别人的锁。云函数超时设为 60 秒（`config.json`），排空循环单次预算 45 秒。
   - **抢到锁的工人**：先补完残留的 `counters/settlement_journal`，再查询所有 `started=true, status='finished', settled!=true` 的比赛，按 `(startTime, _id)` 从早到晚依次结算，直到队列清空才释放锁；释放锁后再复查一次队列防并发漏网。
   - **没抢到锁的请求**：不报错，短轮询最多 3 秒看本场是否已被前一个工人结算完；若尚未轮到，直接返回「已结束，积分结算中」，交由当前在跑的工人继续消费。
   - **定时巡检兜底（每 1 分钟）**：`finishEvent/config.json` 配置了每分钟触发一次的 `drainQueue` 定时触发器。若队列和日志都为空直接返回（零写入）；若因 45 秒预算或异常中断有残留待结算场次，定时触发器会在 1 分钟内自动抢锁继续排空（遇到超过 90 秒的死锁也会自动回收）。
3. **单场结算步骤**（对队列中的每一场）：
   - **超期判定**：开赛已超过 14 天 → 只归档（见 2.5），不改积分。
   - **组装涟漪队列**：本场 + 所有 `settled=true`、`startTime ≥ 本场`、非归档的比赛，按 `(startTime, eventId)` 排序；恢复每人起点；在内存中顺推（每场：拍场内快照 → 算每局 → 累加到每人流动状态）。
   - **Diff**：本场全部写入；后续场次只写 `scoreChange / preScore / preMatches / winner` 有变化的局。
   - **用户增量**：每人 `scoreDelta = Σ新scoreChange − Σ旧scoreChange`（队列内），`users.score += scoreDelta`；`totalMatches / winMatches / loseMatches` **仅按本场新增局累加**（用增量而非覆盖，不抹掉旧友谊赛单局记录与 `fixVirtualScores` 的改动）。
   - **落日志再写**：把要写的 `matches` 补丁和 `users` 的**绝对终值**一并存进 `counters/settlement_journal`，然后依次写 `matches`、`users`、`events`（`settled=true`），最后删日志。任一步中断：日志仍在，事件在队列里（`finished` 且 `!settled`），普通用户无需再操作；任何下一次结算会自动补完，超级管理员也可在「我的 → 结算管理」手动补完或补算。
4. 释放锁。

### 2.4 数字推演（真实引擎输出）
设老张 1000 分 0 局（新手），老陈 1100 分 30 局。周一、周三、周五各一场，每场老张赢老陈一局（单局，`N ≤ 4` 无阻尼）。

| 时间点 | 已结算的场 | 老张每场的加分 | 老张总分 |
| :--- | :--- | :--- | :---: |
| 周五当晚 | 周五 | 周五 +26（1000 对 1100，K=40） | 1026 |
| 周六先补周三 | 周三 → 周五 | 周三 +26；周五进场 1026，**修正为 +24** | 1050 |
| 周六再补周一 | 周一 → 周三 → 周五 | 周一 +26；周三进场 1026，**+24**；周五进场 1050，**+22** | 1072 |

先补周一再补周三，最终仍是 `+26 / +24 / +22`，**1072**。单测 `scripts/test-rating.ts` 用 4 场、4 种结算顺序验证：每种顺序的最终积分与「全部已结算后从头重放」完全一致。

### 2.5 超期兜底（14 天）
开赛后超过 14 天才点结束（以发起人点结束写入的 `finishedAt` 减去 `startTime` 为准，不受排队耗时影响）：**只归档战绩，不改积分**。本场 `matches` 写 `scoreChange=0, settled=true, archived=true`，`events.archived=true, settled=true`，**不动 `users`**。界面提示「已归档，不改积分」。归档场不参与以后任何重放、不进折线图。
（初稿里「按结算当下基准算并写入」会拿含后续各场的当前分当基准，破坏时间线与折线图，已取消。）

## 三、个人主页展示

### 3.1 折线图
- 只画已结算、非归档的约战。横轴按 `matchTime`。
- **一场约战一个点**：`change = 该人本场各局 scoreChange 之和`，`score = 该场 preScore + change`；净变化为 0 也占一个 `+0` 点。展示最近 40 场。
- 最后一个点等于当前积分（在没有旧的友谊赛增减等「重放之外的积分来源」时）。

### 3.2 战绩列表
每局一行：对手、胜/负、日期（取 `matchTime`）。结算后显示该局加减分（`+14` / `-12`）；未结算或归档不显示。

## 四、防呆清单与落地对照

| 项 | 做法 | 位置 |
| :--- | :--- | :--- |
| 全局锁 + 令牌 | `counters/settlement_lock`，90 秒过期，释放校验 token | `finishEvent` |
| 单场幂等 | `events.settled`，已结算直接返回 | `finishEvent` |
| 记分与结算竞态 | 事务里先置 `finished`，记分接口事务内拒绝 | `finishEvent` / `eventSchedule` |
| 写入原子性 | 日志 `settlement_journal` + 幂等应用 + 下次补完 | `finishEvent` |
| 不重复累加场次 | 仅本场新增局累加 `totalMatches/win/lose` | `finishEvent` |
| 增量更新积分 | `score += scoreDelta`，不覆盖 | `finishEvent` |
| 锁死已结束比赛 | `report` / `set` 拒绝；编辑页状态与开赛时间只读；`updateEvent` / `createEvent` 不能设为已结束 | `eventSchedule`、`updateEvent`、`createEvent`、`edit` 页 |
| 已结束/已结算不可删 | 点结束（`finished`）或 `settled` 后隐藏删除按钮，后端拒绝删除；未结束时删比赛会顺带清掉未入账 `matches` | `deleteEvent`、详情页 |
| 未记分对局 | 只看 `events.results`，没记的格子不计分、不计场次 | `finishEvent` |
| 结束确认弹窗 | 「结束后将结算全员积分，未记录的对局不计分，且结束后不可再记分或改判，确认结束吗？」 | 详情页 |
| 比赛时间 | 记分时写 `matchTime`（东八区毫秒）；个人主页按它显示 | `eventSchedule`、`getUserProfile` |
| 分页 | 云库单次最多 100 条，查询按页取 | `finishEvent` |

### 已知限制
- 旧的友谊赛单局记录（改积分、无 `preScore`）不进折线图，也不参与重放；它们的增减仍留在 `users.score` 里。
- 虚拟球友与真人一样入账，发起人可以任意填虚拟球友的胜负来影响真人积分，属于产品层面的已知风险。
- 积分不设上下限，也不是零和（阻尼、保护盾、K 不同都会让同一局赢家所得和输家所失不等），需要观察均值漂移。
- 已有的、被手动改成「已结束」但没结算的旧场次，以及中断未结算完的场次：由超级管理员在「我的 → 结算管理」（`pages/user/settlement`）统一查看并点「结算」或「补完写入」，不暴露给普通发起人。
- `fixVirtualScores` 这类直接改 `users.score` 的工具不拿结算锁；结算期间不要运行。

### 删除与结束并发保护（2026-11-13）

- 删除先在事务里检查权限及结束状态，并写入 `events.deleting=true`，再清理报名、对阵和比赛。
- 结束比赛的事务检查 `deleting`，与删除争用同一份比赛文档。删除先提交则不能结束；结束先提交则不能删除。
- 清理读取或写入失败时不删除比赛、不撤销 `deleting`，发起人再次删除可继续清理。
- 记胜负、报名和取消报名的事务检查 `deleting`；编辑保存会在地址解析完成后通过事务重新检查删除及结束状态，防止旧编辑请求覆盖已结束状态和开赛时间。
- 本地回归：`npm run test:event-lifecycle`，覆盖两种事务交错顺序、清理失败重试、旧编辑请求及删除中记分拦截；数据库采用模拟，部署后仍需验证真实云端行为。
- 这次修改涉及的云函数：`deleteEvent`、`finishEvent`、`updateEvent`、`eventSchedule`、`signupEvent`，需一起部署才能具备完整保护。
